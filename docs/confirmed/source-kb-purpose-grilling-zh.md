# 知识库定位头脑风暴纪要（代码为真源 / 导航索引）

> 本文记录一次关于「RTS 知识库到底该是什么」的逐层追问式讨论。
> 形式：每个决策点钉死后再往下走，最终收敛到一个清晰的定位。
> 结论先行见文末「最终共识」。

## 背景

项目做 XML 转换：上游接收 fixmessage / fpml / mxml 等，转换成
scbml / fpml 等目标格式。技术栈是 Java + XSLT + enum + DOM 等 XML 解析。

现在要建一个**专供 agent 使用**的知识库，做法初步设想是把 codebase 里的
转换逻辑抽象成结构化的 YAML / JSON。发起人对「该不该这么做」产生迷茫，
因此发起头脑风暴（明确不调研已有项目，避免限制思路）。

## 核心区分：两种「把逻辑抽成 YAML」是完全不同的工程

- **A. 知识库 = 给 agent 读的「地图」**：YAML/JSON 从代码**派生**，
  描述「字段 X 在什么条件下映射到字段 Y」。它有损、只读。
  真正干活的引擎仍是 Java/XSLT。
- **B. 知识库 = 新的「真理之源」(DSL)**：YAML/JSON 成为转换的**权威定义**，
  由引擎解释/生成实际转换。代码反而成了 YAML 的产物。

关键风险：XSLT 图灵完备，B 几乎必然撞上「声明式配置表达不了某段逻辑」的
逃生舱问题；A 不会，因为它本就允许有损。

## 逐层追问与决策

### Q1 — 知识库到底服务于哪个目的？

候选目的：1 问答/查询、2 协助新建映射、3 调试/排障、4 改造现有映射、
5 校验/对账。

**发起人选择**：1、3、4、5（排除 2），并补充三件事：
- 需求变更时，通过变更内容（XPath/节点）查找受影响代码范围，知识库同步更新；
- 出问题时通过知识库定位，并能模拟生成对应 XML 片段或完整 XML；
- 代码改动后，借知识库分析影响范围做自动 code review。

### Q2 — 「照着代码写的」vs「照着需求写的」是两份东西

- **照着代码写的**（实况）：代码现在实际怎么转，从 Java/XSLT 扒出来。
- **照着需求写的**（意图）：业务上本该怎么转，从需求文档来，不看代码。

致命点：**不能拿「从代码扒出来的笔记」去校验「那段代码对不对」**——
那是抄了答案再拿抄写判卷子，必然全对、毫无意义。校验（目标 5）必须有
两份来源不同的东西对碰，差异即缺陷候选。

**发起人决定**：先只做「照着代码写的」这一份。「照着需求写的」因为只有
少数项目有业务文档，暂时忽略。对目标 5 做了纠正——真实诉求不是「拿 KB
当标准对账」，而是「生产出问题时重跑真代码费时，想提前模拟跑一遍」。

### Q3 — 「模拟生成 XML」要做到哪个等级？

- **(a) 粗笔记**：给人/agent 看个大概样子，允许不精确。问答、调试够用。
- **(b) 能忠实复现输出**：拿模拟结果判断生产对错，必须把全部条件/默认值/
  格式化/enum/边界都塞进 YAML——等于用 YAML 重写一遍 XSLT。

警告：(b) 就是「第二份实现」，迟早和真代码对不上；而**模拟结果一旦有偏差，
比没有更糟**——拿不准的东西当标尺，等于拿错答案查错题。

**发起人坦白**：最初想要的其实是 (b)。于是转入「b 怎么走才不掉坑」。

### Q4 — b 路线只有两种干净形态，中间地带最烂

- **形态一**：YAML 当老大，Java/XSLT 由它生成。只有一份真东西，永不漂移。
  代价：XSLT 花活要留「逃生口」指向手写代码。
- **形态二**：代码当老大，YAML 是从代码扒出来、有损、且标明哪里扒不动的笔记。
- **最烂的中间地带**：YAML 既不是老大也不从代码生成，和代码并排放的「第二份
  实现」——必然漂移，且模拟不准时比没有更糟。

要它「能跑」其实有两个不同动机：
- **动机甲**：省时间/提前算好（这是缓存问题，用真引擎离线先跑、存结果即可，
  不必维护第二份实现）。
- **动机乙**：让 agent 改映射时改 YAML 而不是改 XSLT（唯一真正划算的理由，
  但必须走形态一）。

### 发起人的关键自悟

发起人自己想穿了两点：
1. **生产级 XML/片段是伪需求**——只要让 agent 自己「算」输出，不管照着 YAML
   还是代码，它必然幻觉。YAML 是不是真源救不了「agent 读完后吐得对不对」。
2. 真正有用的需求是：**改动某处后，借知识库快速生成 testcase（input + expect），
   或从数据库快速捞取所需内容。**

### 正确的 agent 定位：别让 agent 当引擎

把 agent 从「算答案的人」降级成「出题 + 划重点的人」，幻觉毒药就消失：

- **XML 片段问题直接消失**：真引擎跑出完整输出，知识库只告诉 agent「这次改动
  影响输出里的这几个字段」，断言只盯这几个。切片切在「断言」上，不切在「生成」上。
- **生成 testcase 才是 b 真正立得住的形态**：
  1. 改动发生在某 XPath / 规则 / enum；
  2. 知识库告诉 agent「要触发这条规则，输入需满足什么条件」；
  3. agent 据此造 input，或直接去数据库捞一条满足条件的真实消息（捞真实的零幻觉）；
  4. 把 input 喂给**真 Java 引擎**跑 → 得到 expect（真引擎吐的，天生正确）；
  5. 知识库告诉 agent 这条规则影响哪几个字段 → 断言只盯这几个。
  - 此流程里 agent 最多「测错了地方」（一跑就露馅、危害小），绝不会「记录错误的
    expect」（会骗人的毒药）。

### 关键澄清：引擎 vs 知识库不是二选一，是分工

发起人一度纠结「既然有引擎，何必造知识库？直接读代码呗」。拆解：

- **引擎 vs 重造引擎**：想「造个转换引擎」该枪毙——真引擎就在 preprod，能跑；
  再造一个就是「第二份实现」，迟早对不上。引擎负责「算出正确答案」，不可替代。
- **知识库 vs 直接读代码**：知识库不是用来「算答案」的，而是快速回答「该往哪看」。
  直接读代码的硬上限是 agent 一次只能塞有限文件，而一条字段来龙去脉横跨
  XSLT + Java enum + DOM 多个文件。知识库把「散落全仓库的关系」预先压缩成
  一张能一眼查到的索引表，让 agent 知道该去读哪几个文件。

**一句话判据**：
> 凡是「要正确结果」的事 → 走引擎。凡是「要快速定位/导航」的事 → 走知识库。
> 两者都要看真实内容时 → 知识库给坐标，引擎/agent 按坐标去看。

### Q5 — 承重墙：preprod 能否用任意 input 跑真引擎？

这是整座桥的承重墙。能跑 → expect 白送，b 稳；不能跑 → 被逼回让 agent
模拟 expect，毒药回来。「重不重」的真正变量不是 CPU（XSLT 转一条通常毫秒级），
而是**喂数入口**好不好触发。

**发起人确认**：可以。preprod 上的生产服务可直接丢一个 input 让它 consume，
产出可落本地或数据库。→ **承重墙立住，b 路线正式成立。**

### Q6 — 知识库记什么？（待发起人确认）

导航索引只记三样、坚决不记一样：
- **记 What**：哪个输入字段/XPath → 哪个输出字段/XPath。
- **记 Where**：这条映射在哪个文件、哪个 XSLT 模板/Java 方法实现（代码坐标）。
- **记 When**：这条映射在什么条件下才生效（门槛条件，是「造 input 触发」的关键）。
- **坚决不记 How**：具体怎么算（日期怎么拼、字符串怎么处理）——那是引擎的活，
  只打标签「这里是计算逻辑，见文件 X」。
- **唯一例外 enum**：enum 映射的 How 本身是纯数据查找表（A→X, B→Y），无逻辑，
  应整张表记进去——它是数据，不是「重写逻辑」。

最小单元（一条「映射规则」）：源 / 目标 / 条件 / 实现位置 / 类型（直接搬运 |
enum查表 | 计算 | 常量）/（仅 enum）完整值对照表。

「不记计算型 How」是命脉：它让知识库天生有损、永不假装能跑，从而永远只是
「地图」，不会退化成「山寨引擎」。

**留给发起人的两个问题**（本次讨论暂停于此）：
1. 映射里「计算型」（XSLT 花活）占多大比例？绝大多数是搬运+enum → 地图覆盖
   ~90% 需求，划算；一大半是计算型 → 地图上多是「见代码 X」空洞，需重新掂量。
2. 那个「条件/门槛」能否从代码干净扒出？还是藏在嵌套 `<xsl:if>`/`<xsl:choose>`
   里难以提取？这直接决定「造 input 触发规则」靠不靠谱。

## 最终共识

钉死的结论（已与发起人确认）：

1. **代码是唯一真源，知识库是从代码派生的「只读导航索引」**（前述形态二 / A 路线）。
   知识库**永不当引擎、永不当真源**。代码一改，重新派生即可，结构上不可能漂移。
2. **真转换引擎只有一个，在 preprod，永不重造。** 它负责「算出正确答案」。
3. **agent 不算输出。** agent 的角色是「出题（造/捞 input）+ 划重点（该盯哪些字段）」，
   不是「算 expect」。expect 一律由真引擎跑出。
4. **核心工作流 = 生成 testcase**：知识库给「触发条件 + 影响字段」→ agent 造或从库捞
   一条 input → 真引擎跑出 expect → 断言只盯受影响字段。
5. **校验/对账（原目标 5「拿 KB 当标准」）暂时搁置**：需要独立的「照着需求写的」第二份
   来源，而多数项目无业务文档。先不做。
6. **知识库边界**：记 What / Where / When + enum 全表；坚决不记计算型 How（只打标签
   指向代码）。这条边界是命脉，保证知识库永远是「地图」而非「山寨引擎」。

一句话判据（反复纠结时回到这句）：
> 要正确结果 → 走引擎；要快速定位/导航 → 走知识库；两者都要看真实内容 →
> 知识库给坐标，引擎/agent 按坐标去看。

## 给接续者（新 session / 新 agent）的说明

**本次讨论的性质**：这是一次「该不该建知识库、建成什么样」的方向性头脑风暴，
**尚未进入实现**。没有写任何代码，没有定文件格式细节，没有定字段 schema。

**讨论暂停在 Q6**：定位与边界已共识（见上），但还差两个事实没确认，需要**通过实际
探查 codebase 来回答，不要凭空假设**：

1. 映射中「计算型逻辑」(XSLT 花活) vs「直接搬运 + enum 查表」的**实际比例**。
   - 若绝大多数是搬运+enum → 地图覆盖 ~90% 需求，强烈划算，继续推进。
   - 若一大半是计算型 → 地图上多为「见代码 X」空洞，需重新掂量 ROI。
2. 触发条件/门槛能否**从代码干净提取**，还是深埋在嵌套 `<xsl:if>` / `<xsl:choose>`
   中难以结构化。这决定「造 input 精准触发某规则」是否可靠。

**接续建议**：先探查 codebase 回答上面两点（建议抽样几个有代表性的转换看比例与
条件复杂度），再据此决定知识库的具体 schema 与提取方式。在那之前不要急于定 YAML 格式。

**绝不可动摇的前提**（若想推翻，必须显式重新论证，不要默默改）：
- 知识库不算输出、不当引擎、不当真源；
- expect 永远来自真引擎；
- 不记计算型 How。
